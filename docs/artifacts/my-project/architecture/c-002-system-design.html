Ops AI runtime: how a workflow with agents, evals, fan-out and handovers runs

c-002 · ops-ai · architecture · system design · 2026-10-10

The runtime that executes published workflows, agent runs and chat sessions for the Ops AI console, on either of two execution engines, Temporal or LangGraph on PostgreSQL, behind one seam. Sources: docs/architecture/service-map.md, specs 14–17, ADR-0001..0015.

What changed

  • First version. Supersedes the stub wiki pages that said no architecture was found.
  • Nothing is decided. Every ADR is an option with a recommendation; the design keeps a seam at each choice so a deployment can pick differently. The seams table below is the contract.
  • Slice 1 (chat on the real runtime) is live: OpenAI gpt-5.5, Pydantic AI kernel, approval with step-up, PostgreSQL. Section "The prototype at the bottom" shows how. The engine seam arrives with the first workflow run.

Context

Back-office staff at a bank (Northfield is the demo tenant) run agents and workflows from the Ops AI console. The runtime executes them; everything it touches outside itself goes through a gateway or the control plane.

Actor / external systemRelationship
Ops staff (console)Chat with agents, watch runs in Cases, decide reviews. Reach the runtime only through the console BFF.
Builders and approvers (console)Author definitions, request and approve publishes in the control plane; the runtime reads the result as a compiled plan by digest.
Outside assistantsCall published workflows over the MCP and API channels; each call starts a run.
Shared mailboxes (Microsoft Graph)mailbox-intake polls delta every 60 s and starts a run per new mail.
Bank systems (CRM, core, mail, MCP servers)Reached only through the data gateway, which decides with OPA and checks approval tokens on writes.
Model providers (Anthropic, OpenAI, bank-hosted)Reached only through the AI gateway; workers hold no model keys. Slice 1 uses a direct key from the environment as a stand-in.
Bank IdP (Entra, Okta)Signs people in (spec 13); issues the delegation tokens a run acts under (ADR-0005).
Control planeRegistry, versions, release pointers, cases, reviews, audit. Owns every approval token; the runtime only verifies them.

One approval

The turn pauses with its model history saved; approval resumes the same turn through Pydantic AI's deferred tools, so the model finishes its own sentence.

One complex workflow, step by step

A dispute email with attachments. The definition below uses every node kind the owner asked about: a loop over items with fan-out, an agent per item, an agent that grades (an eval inside the run), a condition that loops back, a policy gate, a handover to a person, and a write that needs the person's approval. Node kinds are from spec 16 §3; the agent turn inside each agent node is spec 15.

Risks

  • Two engines double the conformance surface. Mitigation: the eight-test conformance suite in ADR-0015 runs on both adapters in CI; plans may not carry engine-specific settings.
  • The LangGraph adapter proves resume, not determinism. Mitigation: side-effecting nodes are idempotent by key, write class gets one attempt plus a reconciliation read.
  • DBOS may beat LangGraph for engine B. Mitigation: one-week spike against the conformance suite before the adapter is extended past slice needs.
  • Compiled wheels (Temporal Rust core, pydantic-core, asyncpg) may be blocked by a source-only mirror. Mitigation: the dependency manifest names each; builds from source are documented.
  • psycopg is LGPL. Mitigation: unmodified use, legal sign-off recorded.
  • AI SDK 7 is current and Protobox is on 6. Mitigation: the console targets 6 until Protobox moves; the kernel's stream adapter is pinned to 6.
  • Slice 1 chat is not durable and tools are in-process. Mitigation: each stand-in sits behind the same interface as the real gateway and is replaced by its own card.
