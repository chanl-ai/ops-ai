## What it does

A department uploads text PDFs (or markdown and text files) into a file source, a knowledge base reads that source,
and an agent granted the knowledge base cites passages from it by document, version, page and section.

| Part | Detail |
|---|---|
| Knowledge bases | Created with a required owner (`collection_without_owner`), named uniquely per tenant, optionally under a caller-chosen id (`kb_[a-z0-9_]+`). Listed and paged on the server with the console's `page`, `pageSize` and `search` |
| Sources | Four kinds: `file`, `text` (typed text), `push` and `tool` (a plugin's knowledge source); any other type answers 400 `type_unsupported_in_phase`. A source holds file ids. Files are uploaded to files-service first; `POST /v1/sources/{id}/files` {fileIds} adds them, each the team's and scanned clean, and records a reference so Files keeps it while the source reads it. `POST /v1/knowledge-bases/{id}/documents` {fileIds} is the console's one-click Add documents: it makes or reuses the base's documents source, found by the id the base records (`kb_bases.documents_source_id`, so a rename never makes a second one), adds the files through the same check and syncs. Both routes refuse the same files (`test_both_add_routes_refuse_the_same_files`), and a refused batch releases the Files references it took for the ids before the refused one. kb-service writes bytes itself only for written items and the dev-start seed |
| Typed text and push | `POST /v1/sources/{id}/items` {name, title?, text \| content, mime?} writes one item into a `text` or `push` source (400 `source_not_written` for another kind): `text` is Markdown by default (a title becomes its heading; text/plain and text/html by `mime`), `content` is base64 bytes of a file such as a PDF. The item is stored in files-service like an upload and indexed by the source's sync at once; the answer says `created`, `updated` or `unchanged`. The same name with the same content is `unchanged` and starts no run, so a caller may resend safely; new content is the item's next version (`tests/test_written_sources.py`). The console's Add a page writes into the base's own `text` source. Each write that changes something runs one sync of its source, which describes every file the source holds, so a push source of many thousand items pays that per write |
| Sync | `POST /v1/sources/{id}/sync`, body `{full?, retry?}` and nothing else (400 for an unknown field). Each file is parsed and split with `ops_ingest` (headings become sections, chunks carry page and section). A new name is a new document; a known name with new content is its next version, written with its chunks in the transaction that withdraws the old version's chunks and records a change row. `full` and `retry` rebuild documents from the same content under their current version. A PDF with no text layer fails that document with `no_text_layer`; the rest index. Every sync is a run (`/v1/sources/{id}/runs`, `/v1/sync-runs/{id}`) |
| Cleaning | Applied between reading and splitting, from the source's `cleaning`: `furniture` drops the blocks the reading marked as page furniture and the boilerplate lines of `ops_ingest`'s `clean`; `mainContent` keeps only the page's main or article element when it has one; `duplicates` compares each item's text after cleaning (`content_digest`) with the indexed items of every knowledge base its source feeds: `flag` (default) leaves the older copy out of search (`duplicateOf`) and says so on both, `skip` keeps the new copy out (status `skipped`). Lines repeated across a site (`siteRepeats`) are counted per website source (Source kinds below). Content a plugin tool gives has no reading yet and is cleaned as it is parsed |
| Item detail | `GET /v1/items/{id}` shows how the item was read and cleaned page by page (`reading`: read by text, OCR or both, the blocks kept, the characters cleaning removed, the OCR confidence), each piece with the units it is searched as and its metadata, and the split it was built under (`settingsUsed`, with `current` false while a rebuild is due); the file id opens the copy that version was built from |
| Rebuild | A settings save that changes reading, cleaning, splitting or metadata starts a rebuild in the background (`rebuild` on the save's answer, trigger `settings`): each item built under other settings is split again from its stored reading, or read again when the OCR mode changed, keeping its version; nothing is fetched from where it came from. The run holds the source's lease, so a sync answers 409 `sync_running` beside it; it reports progress in its counts (`total`, `checked`, `rebuilt`, `reading`, `failed`, `skipped`) and stops between two items after `POST /v1/sync-runs/{id}/cancel` (409 `run_not_running` otherwise). A run a stopped process left running is ended by the knowledge schedule after 15 minutes, saying why. Every file sync holds the same lease |
| Source kinds | `GET /v1/knowledge/source-kinds`: Files, then each knowledge source of the team's apps that are on, with whether it needs and has a working connection, whether it previews or has pickers, whether its items are one website's pages, and what it is set up with; Add source lists exactly these. A website source (`site`) starts with a website's cleaning and splitting: furniture dropped, the main content kept, lines repeated across the site dropped, split at headings with context headers. After each sync of a website source the lines found on more than half its pages (three pages or more) are counted; when they change, the pages built under the old set are rebuilt in the background from their snapshots |
| Re-sync cost | A new version keeps each live piece whose text and units are unchanged (its id, units and vectors), moved to its new place and version, and withdraws the rest; withdrawn pieces are deleted 30 days later by the schedule beat. A fetched item whose cleaned text is unchanged (a page with no change signal served with a new timestamp) keeps its version and records only its new markers. A listing longer than a run's 200 calls fetches what it found, saves its cursor and what it has listed so far (`seenSoFar`), and the run that finishes it removes what left the listing. Fetches keep to the source's rate, or the slower pace its listing names (`pace_s`, a site's Crawl-delay) |
| Leases | A sync or rebuild takes its source's lease with an owner token (`lease_owner`, kb_0023) for two minutes by the database's clock, renews it every 40 seconds while it runs and releases only its own. A run still marked running is ended as stopped only when its source's lease has lapsed, however long it has run |
| Schedule and health | Every source of every kind syncs on its own by the one schedule rule (`ops_store.schedule`): `manual`, `hourly` every 1, 2, 4, 6 or 12 hours, `daily` at a time, or `weekly` on a day, in the schedule's `tz`. A source's `schedule` is a setting (400 `invalid_settings` for a bad one); left out, a plugin source uses its plugin's, a website source checks daily at 02:00 UTC, and a file source is manual. Each source shows `nextSyncAt` and `health`: never, healthy, failing (since when, days, runs in a row) or needs_reconnect, and how many addresses are tombstoned. The second failed run in a row writes `knowledge.source.failing` to the outbox, which the relay delivers to agents-service's `/v1/events` so a workflow can tell the owner. An item a plugin answers gone (NOT_FOUND) on two syncs in a row is removed and its address tombstoned: a later listing leaves it out until `POST /v1/sources/{id}/tombstones/lift`; `GET .../tombstones` lists them |
| Plugin sources | A `tool` source names a plugin's knowledge source and its own `values` (checked against the inputs the plugin declares, 400 `invalid_source_values`), sent to every call as `source`. A sync lists through the plugin's changes tool when it has one, sends the version tag it holds so an unchanged item answers `unchanged`, takes in content a listing already read, leaves out and removes skipped items with their reason, removes items the system reports deleted, and for a source whose listing is whole (a website) removes on every run what left it. A deleting run only removes after a listing read from its first page. `POST /v1/sources/preview` asks the plugin's preview what a source would take in and stores nothing |
| Snapshots | Every item a plugin source fetches is stored in files-service as a `knowledge_snapshot` file, referenced by the source, before it is read, and read through documents-service like any file: kb-service parses nothing itself. A rebuild reads the snapshot and calls the system for nothing; a citation carries the snapshot's `fileId` and the item's `url`. When a newer version or a delete replaces an item, its old snapshot is let go and files-service keeps it 30 days more |
| Index units | What search matches is kept apart from what it cites (`kb_units`, kb_0016): each piece (`kb_chunks`) is searched as its own text with its context header, its smaller children under parent and child, and the questions written for it, and a match on any unit returns and cites the piece, once, naming the unit that matched (`matched`). One document gives at most two pieces to an answer. Each piece carries the metadata its source maps (`metadataMapping`), shown with its units on the item's detail |
| Retrieval | One search (`retrieval.py`, `search.py`) serves every caller: M1 `POST /v1/knowledge-bases/search` (grounding and the search_knowledge tool, through agents-service and tools-service) and K12 `POST /v1/knowledge-bases/{id}/query` (the query route and the Playground; 409 `not_indexed` before any sync). Two lanes: keyword (`store/fulltext.py`), a unit scored by the share of the question's terms it holds (and two shared terms when the question has two); meaning (`store/vectors.py`), the cosine similarity of the question's vector to the unit's in pgvector. Each lane drops what is under its own floor: the keyword lane under the base's `threshold` (a share of terms, 0.5), the meaning lane under `meaningThreshold` (cosine similarity, 0.30 by default, below the answering passages and above unrelated ones for OpenAI's text-embedding-3 models; a base on another model sets its own). The meaning search runs pgvector's iterative HNSW scan (`hnsw.iterative_scan = relaxed_order`, `ops_store.dialect.vector_search_setup`), so a small base beside a large one still gets its nearest pieces; a meaning lane whose index answered no candidate is reported skipped (`no_candidates`), not run; the rest are fused by reciprocal rank (k = 60) weighted toward meaning by `hybridWeight`, each piece once by its best unit, at most two per item, up to `chunkLimit`. The base's `searchMode` (`hybrid` by default; `keyword` or `meaning`) picks the lanes. Several bases in one search use every lane any asks for, the lowest threshold, the mean weight and the largest limit; a caller's `limit` only caps it. Every result lists the lanes asked, run and skipped with the reason (`no_embedding_model`, `no_vector_store`, `no_vectors`, `embedding_unavailable: <code>`; the keyword lane's `no_full_text` on a database without full-text search), each passage's score per lane, `verified`, and the embedding tokens the question cost |
| Rerank and rewrite | Two steps around every search (`query_steps.py`), both off until a base's owner turns them on in its retrieval settings, both called through models-service with kb-service's key (step `kb:query`) on the base's `queryModel` alias, or the environment's `OPS_KB_QUERY_ALIAS` (bank-standard) when it names none. `rewrite: "rewrite"` asks the model to rewrite the question with `rewriteInstructions` before the lanes run; the answer's `rewrite` holds the question as asked and as searched. `rerank: true` has the model score the best 20 fused pieces from 0 to 10; the pieces returned follow its order, cut to the base's limit, each with its `reranked` score, and the answer's `rerank` says it ran, on which alias and how many it scored. A step whose model cannot answer leaves the search as it would have been, with `skipped` and the reason (`no_query_model`, `model_unavailable: <code>`, `unreadable_answer`); a search never fails because a model did. Over several bases, rerank runs when any base asks and the rewrite follows the first base, in the order named, that rewrites. Rewrite `expand` is refused (400 `invalid_retrieval`). Both steps serve every caller of the one search: grounding, the search tool and the Playground (`tests/test_rerank_and_rewrite.py`, uc-677). Their model spend is recorded by models-service against kb-service's key and is not yet returned on the answer |
| What a source and a base show | A source says its `kind` (file; web, a plugin source of one site's pages; or tool) its kind in words (`kindLabel`: Files, or the title its plugin declares, kept on the source when it is made), what it takes in (`scopeSummary`: a site's start address, or a plugin source's name, or its files), and the AI steps chosen and still waiting for the knowledge owner's approval (`aiStepsWaiting`). A website source whose host the account has not listed waits for an admin's approval under the account's new-hosts policy: adding it asks tools-service as the person adding it, the source lists `waitingHosts` (each with the Security task's `runKey` when Security was asked), its syncs and preview answer 409 `host_waiting` with nothing fetched, and the schedule syncs it once approved (`test_a_builders_new_site_is_fetched_only_once_an_admin_approves_its_host`). The console shows these as given and keeps no list of kinds of its own. A source read through an app keeps its own settings in `config.values` (a site's start, include and exclude, depth, pace), edited with `PATCH /v1/sources/{id}` `{values}`, merged and checked against what its plugin declares (400 `invalid_source_values`). A base's detail says how many of its units are embedded with the environment's model (`embedding`) |
| Likely questions | A source's AI step `faq` (Settings: likely questions) writes up to `questionsPerSection` questions per piece, kept as index units of kind `question`: they help search find the piece and never reach the answer. Nothing is written until the knowledge owner approves the steps as chosen (`POST /v1/sources/{id}/ai-approval` `{decision: approve|revoke}`, written to the audit log; approving rebuilds the pieces in the background). `GET /v1/sources/{id}/ai-estimate` splits up to 20 indexed items with no model called and scales the calls and tokens to the source, saying its basis (the price per token stays at models-service). The split runs in a worker thread through models-service with kb-service's key (step `kb:questions`); a piece whose text had questions keeps them with no call (`piece_digest`). Each run carries its own id and its source's ceiling in money (`aiCeiling`, $5 by default) to models-service, which refuses a call once what it recorded for the run reaches it (429 `run_spend_cap`); kb-service's key also stops for the day at the environment's cap (`OPS_KB_AI_DAILY_CAP`, $50, models-service `daily_spend_cap`). Past either, or with the model down, the rest of the pieces are indexed without questions and the run's log says why. Each run records `modelCalls`, `inputTokens` and `outputTokens` |
| FAQ drafts | A source's AI step `faq_pairs` (Settings: FAQ drafts; approved with the other AI steps) drafts up to 8 question-and-answer pairs per section, each with the exact words of the section it came from (a pair quoting text not in its section is dropped). Drafts wait in the Changes queue (`GET /v1/knowledge-changes?view=open`, origin `generated_faq`, the quoted passage as `before`; `origin=` filters on the server, the facet counts the view before it, and `canDecide` is true only for a caller who may change the source) for the knowledge owner: `POST /v1/knowledge-changes/decide` `{ids, decision: approve|reject}` for one or many, `PATCH /v1/knowledge-changes/{id}` to edit the question and answer (still pending; 409 `draft_decided` once decided). An approved pair is an index unit of kind `faq` of the piece holding its quote, so search returns and cites the source passage with the question as its best match. Only sections whose text changed are drafted again: their pending drafts are superseded and their approved pairs marked `source_changed` for a second look (still searchable while the quote is found) |
| Embeddings | Every index unit is embedded with the environment's model (`OPS_EMBEDDING_ALIAS` at `OPS_EMBEDDING_WIDTH`) through models-service with kb-service's own key (`OPS_MODELS_KEY`, step `kb:index`), stored in `kb_unit_vectors` (kb_0021, PostgreSQL with pgvector only) with the model and width it was made with, under an HNSW index for the environment's width. A sync or rebuild embeds its tenant's new units as it settles; a model that is down leaves them to the `kb_embed` process (every 30 s), and the sync does not fail for it. A new model or width embeds every unit again and reads no file again. `/health` reports `unitsNotEmbedded` after each pass; a base's detail its coverage |
| Source settings | Each source keeps its stages' settings in `kb_sources.settings` (`source_settings.py`): `parsing.ocr` (`off`, `auto`, `always`; the environment's `OPS_KB_OCR` is the default), `cleaning` (furniture, main content, lines repeated across the site, duplicates), `ingest` (the `ops_ingest` split: preset, strategies, piece size and overlap, child size, questions, table columns, model, AI-step approval), `rules` (include and exclude on path, title, type, modified date, size) and `metadataMapping`. A save is merged key by key and validated as a whole (400 `invalid_settings` naming the setting); it never changes the AI-step approval, and an AI step added since is pending again. Defaults by kind: files split at headings with context headers (what every file source was indexed with before), web sources clean furniture and keep main content. A sync reads with the source's OCR mode, splits with its ingest settings and leaves out what its rules exclude, removing an excluded item already indexed. Each item records the settings digest it was built under (`indexed_with`); `reindexNeeded` on the source is true while any item was built under other settings or read with another OCR mode, and the next sync rebuilds those items from their stored readings |
| Audit | A change to a knowledge base's or a source's settings writes one entry naming each changed field before and after (a nested setting, its changed keys) to `kb_outbox` in the change's transaction; the `kb_relay` process delivers it to platform-service's audit log (`ops_store.audit`), where the Audit page shows it. A save that changes nothing writes none |
| Changes | `GET /v1/knowledge-changes` lists who replaced which document, from and to which version, with the first changed section before and after, and the FAQ drafts waiting for review. The view (open, mine, resolved, all), base, search and origin are filtered, counted and paged in the database (`KnowledgeStore.change_page`), and the sources and bases a page names are read once for it (`test_the_queue_pages_in_the_database_and_reads_sources_once_per_page`) |
| Team | A base, a source and everything under them (links, documents, versions, chunks, changes, runs) belong to one team, and the database holds every kb transaction to it (kb_0011, role `ops_kb_tenant`). A base's name is unique in its team; an id another team holds answers 409 with no team named. "Used by" names and counts the acting team's agents only | `store/knowledge.py`, `tests/test_kb_isolation.py` |
| Who may change what | A knowledge base: its owner or a tenant admin (update, attach and detach, refresh, delete). A source: its owner or an admin (upload, sync, edit, pause, remove). A document: its owner, its source's owner or an admin (verify, owner). An admin is an admin in any of the caller's teams; there is no tenant-wide role yet |

## How agents use it

agents-service with `OPS_KB_URL` asks kb-service for the tenant's knowledge bases when a thread opens (a thread may
only name knowledge bases the agent holds) and for passages on each turn, cut to the agent's grants as they are then.
Without `OPS_KB_URL` it serves no knowledge: opening a thread on knowledge answers 503 `knowledge_unavailable`, and an
agent with no knowledge bases works as before. Unit tests inject a fixture store through `create_app(knowledge=...)`
(`services/agents-service/tests/knowledge_fixture.py`); no service path falls back to it. The use-case harnesses start
a kb-service per run and fill it with the agents fixtures' knowledge through this API
(`docs/usecases/lib/seed_fixture_knowledge.py`).

## Run it

| Do | How |
|---|---|
| Serve | `make up` runs it on the shared stack; alone, `make -C services/kb-service run` |
| Migrate | `make -C services/kb-service migrate` |
| Verify | `make -C services/kb-service verify` (lint, strict pyright, tests on the test database, OpenAPI gate) |
| Seed the demo | `uv run python scripts/seed_demo_knowledge.py` in `services/kb-service` |
