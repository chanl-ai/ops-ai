What Ops AI is

Ops AI is an operational AI platform: AI agents and workflows that do back-office work, with a person approving every action that changes something outside it. People use one web console to see what the agents did, decide what waits on them, and configure agents, workflows, tools, knowledge and documents. Every write to another system goes through a gateway that checks an approval, and every record is kept per tenant and team.

Ops AI stores everything in one PostgreSQL database. Your DBA applies the schema in your own change window, and the services connect with logins that can read and write rows but cannot change the schema.

The logins

LoginWho uses itRights
Your server adminThe DBA, for the steps belowCreates the roles and the database. Not a superuser on Azure
ops_migratorThe DBA, to apply and upgrade the schemaOwns every table, index and policy; cannot create roles or databases
ops_platform_runtime, ops_agents_runtime, ops_tools_runtime, ops_models_runtime, ops_kb_runtime, ops_files_runtime, ops_documents_runtimeOne per serviceRead and write rows in that service's own tables. No DDL: CREATE TABLE, DROP TABLE and ALTER TABLE are refused. Row-level security applies
ops_runtime_tenant, ops_runtime_system, ops_platform_tenant, ops_platform_lookupThe services switch to these inside a transactionNo login. ops_runtime_system reads across tenants and is used only by the agents service's background loops

Tenant isolation

Every table that holds customer data carries a tenant_id column and a row-level security policy that admits only rows whose tenant_id equals the tenant the transaction set. The policies are forced, so they apply to the table owner too. The tenant comes from the signed-in person's token, never from a request body.

What the DBA runs, in order

In the folder db/postgres/ of the unpacked package. <admin> is your server admin; <host> is your server's name.

StepConnect asCommand
1Server adminpsql -v ON_ERROR_STOP=1 "host=<host> port=5432 user=<admin> dbname=postgres sslmode=require" -f roles.sql
2Server adminpsql -v ON_ERROR_STOP=1 "<same as step 1>" -c "ALTER ROLE <login> PASSWORD '<password>'" once for each of the eight logins in the table above
3Server adminpsql -v ON_ERROR_STOP=1 "<same as step 1>" -c "GRANT ops_migrator TO <admin>"
4Server adminpsql -v ON_ERROR_STOP=1 "<same as step 1>" -c "CREATE DATABASE ops OWNER ops_migrator"
5ops_migratorpsql -v ON_ERROR_STOP=1 "host=<host> port=5432 user=ops_migrator dbname=ops sslmode=require" -f bundle.sql
6ops_migratorpsql -v ON_ERROR_STOP=1 "<same as step 5>" -f grants.sql

01-agents.sql to 07-documents.sql are each service's part of bundle.sql, for review. manifest.json names each part's version; sha256sum -c SHA256SUMS checks the files.

Install

On the VM, as a user that may run Docker, in a folder only your operators can read.

  1. Check and unpack the files you copied to the VM.

    sha256sum -c ops-ai-<version>.SHA256SUMS
tar -xzf ops-ai-<version>.tar.gz
cd ops-ai-<version>
sha256sum -c SHA256SUMS

  2. Load the images, then compare docker images with images.txt.

    docker load -i ../ops-ai-<version>-images.tar.gz

  3. Make the settings file from the template.

    cp ops-ai.env.example ops-ai.env
chmod 600 ops-ai.env
docker run --rm --entrypoint python <OPS_IMAGE_PREFIX>/platform:<version> /app/deploy/fly/generate_keys.py

    The last command prints the signing keys. Put each printed line in ops-ai.env in place of the empty line with the same name. Then set these:

    SettingValue
    OPS_PUBLIC_ORIGINThe address people open, for example https://ops.example.com
    OPS_PUBLIC_PORTThe entry point's port on the VM
    OPS_DATABASE_URL_PLATFORM and the six other OPS_DATABASE_URL_<SERVICE>postgresql+asyncpg://ops_<service>_runtime:<password>@<host>:5432/ops?ssl=require
    OPS_DATABASE_URLLeave empty
    OPS_BOOTSTRAP_TENANT_NAME, OPS_BOOTSTRAP_ADMIN_EMAIL, OPS_BOOTSTRAP_ADMIN_NAME, OPS_BOOTSTRAP_ADMIN_PASSWORDYour organisation's name and the first admin; the password has at least 12 characters

  4. Start everything except the agents.

    C="docker compose -p ops-ai -f compose/app.yaml -f compose/dba.yaml --env-file ops-ai.env"
$C up -d --wait --wait-timeout 600 migrate platform tools models kb files opa

    The first job makes the first tenant, its Security team and the admin. Every service checks the database's schema version and refuses to start when it is older than the service.

  5. Connect a model. This binds the name default to your OpenAI-compatible endpoint and prints a key once; run it twice, once per key id.

    $C run --rm -T --no-deps agents python /app/deploy/fly/connect_model.py --models-url http://models:8730 \
  --base-url <endpoint>/v1 --alias default --model <model id> --input-price <per million tokens> \
  --output-price <per million tokens> --budget <spending cap> --key-id purpose:agents

    Put the printed OPS_MODELS_KEY value in OPS_MODELS_KEY_AGENTS, run it again with --key-id purpose:documents and put that value in OPS_MODELS_KEY_DOCUMENTS. When your endpoint needs a key, the Security admin stores it in Settings > Secrets and you add --key-ref <its name>; the proof used the test model, which needs none.

  6. Start the rest.

    $C up -d --wait --wait-timeout 600

To try the package before your database and model are ready, add -f compose/try.yaml --profile fake-model to C and connect the model with --base-url http://fake-model:8746/v1 --model fake-chat --input-price 1 --output-price 1 --budget 5. The test model answers from fixed rules and is not for production.

Upgrade and roll back

StepWhoWhat
1DBABack up the database (below)
2OperatorLoad the new release's images with docker load
3DBARun the new release's db/postgres/upgrade-from-<your version>/upgrade.sql as ops_migrator, then its grants.sql. Each step checks the version it starts from and stops before any change when the database is elsewhere
4OperatorSet OPS_IMAGE_TAG to the new version and run $C up -d --wait --wait-timeout 600

This release is the first, so it holds no upgrade script; each later release ships one from the versions before it. To roll back, restore the backup from step 1 and set OPS_IMAGE_TAG back. A service of the older release refuses to start on the newer schema, so the two cannot be mixed by mistake.

Back up and restore

On Azure, the automated backups and point-in-time restore cover the database. For a copy you hold yourself, back up as the server admin: the tenant policies apply to the schema's owner, so pg_dump as ops_migrator stops with a row-level security error. Use pg_dump of your server's version or newer; the postgres image carries one.

docker run --rm -e PGPASSWORD=<admin password> -v "$PWD/backup:/backup" postgres:17 \
  pg_dump -Fc -f /backup/ops.dump "host=<host> port=5432 user=<admin> dbname=ops sslmode=require"
docker run --rm -v ops-ai_files-data:/data -v "$PWD/backup:/out" alpine tar czf /out/files-data.tgz -C /data .
docker run --rm -v ops-ai_kb-data:/data -v "$PWD/backup:/out" alpine tar czf /out/kb-data.tgz -C /data .

Keep ops-ai.env with the backup: OPS_SECRETS_KEY unlocks the stored credentials, and without it they are lost.

To restore into a new database:

$C stop
psql -v ON_ERROR_STOP=1 "host=<host> port=5432 user=<admin> dbname=postgres sslmode=require" -c "CREATE DATABASE ops_restored OWNER ops_migrator"
docker run --rm -e PGPASSWORD=<admin password> -v "$PWD/backup:/backup" postgres:17 \
  pg_restore --exit-on-error -d "host=<host> port=5432 user=<admin> dbname=ops_restored sslmode=require" /backup/ops.dump
docker run --rm -v ops-ai_files-data:/data -v "$PWD/backup:/in" alpine sh -c "rm -rf /data/* && tar xzf /in/files-data.tgz -C /data"
docker run --rm -v ops-ai_kb-data:/data -v "$PWD/backup:/in" alpine sh -c "rm -rf /data/* && tar xzf /in/kb-data.tgz -C /data"

Point the seven OPS_DATABASE_URL_<SERVICE> settings at ops_restored, then $C up -d --wait --wait-timeout 600.

Security notes

AreaWhat holds
SecretsAll in ops-ai.env (mode 600), or each as a file under /run/secrets named after the setting in lower case, for Docker secrets. No image holds a secret
KeysOne signing key per service, handed only to that service; OPS_PLATFORM_SIGNING_KEY signs sign-in tokens; OPS_REVIEW_KEY signs approvals; OPS_SECRETS_KEY seals stored credentials. Keep them out of tickets and chat
DatabaseEach service has its own login with row rights on its own tables only; no running container can change the schema; row-level security separates tenants
NetworkOnly the entry point publishes a port. The services, the policy engine and platform-service's internal port stay on the Compose project's private network. Put TLS in front of the entry point
Outbound callsTool calls leave only through the tools service, under its policy engine; model calls only through the models service
ContainersEvery image runs as a non-root user (uid 10001)
First adminRemove OPS_BOOTSTRAP_ADMIN_PASSWORD once the admin has signed in and changed it

Azure SQL

The scripts are generated from the services' models and checked against reviewed copies, but they have never been applied to a server, and Ops AI does not run on SQL Server yet. Install on PostgreSQL today.

Ready for review in db/azure-sql/

  • roles.sql: one SQL login per service and ops_migrator; the database with collation Latin1_General_100_BIN2_UTF8 and READ_COMMITTED_SNAPSHOT ON
  • 01-agents.sql to 07-documents.sql and bundle.sql: every table, index and key, and a security policy per tenant table
  • grants.sql: each service's user with SELECT, INSERT, UPDATE and DELETE on its own tables only
