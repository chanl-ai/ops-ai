Ops AI architecture

Ops AI is an open-source platform that lets an enterprise's operations teams hand routine work to AI, with a person approving anything that moves money or changes a record. It runs work in two ways: agents, which decide their next step within set limits, and workflows, which run the same typed steps every time. A deployment can run either or both. All work reaches business systems and AI models only through two gateways, and stores its state in a SQL database the enterprise provides.

Ops AI is pre-release. Each part carries a status label for what is in code today.

Agents inside workflows, workflows as agent tools

partial
  • A workflow step that needs judgement starts an agent run and receives its output in a declared schema.
  • An agent can call a published workflow as a tool, found by search and available only when granted.

Both links work today through adapters inside agents-service. Moving each onto the public run APIs is planned, so that a deployment with only agents, or only workflows, runs on its own.

Services every run uses

Identity and teams, reviews and cases, triggers and timers, knowledge, files and the work feed serve agents and workflows alike. Every write passes the data gateway with its approval policy and fails closed.

Why agents and workflows run separatelyAgents and workflows fail in different ways and are reviewed in different ways: an agent is judged on its answers, a workflow on its steps. Separate run APIs let each be tested, approved and deployed on its own, and a fault in one stays inside its own data. The cost is maintaining the two links between them, which is smaller than tying every agent change to the workflow engine.

5 Agents

An agent is an instruction, a model alias and its attachments: tools, knowledge, skills, guardrails and a budget. It is versioned, goes live through a publish review, and decides its own next step inside those limits. Every way of using an agent, from a chat message to a scheduled job, is a run on one agent run API.

What a caller may change per run

partial

The published agent sets defaults and limits. A caller or the chat UI may:

  • choose a model from the agent's allowed list, and a temperature within its range;
  • add to the instructions;
  • narrow the tools, and choose or narrow the knowledge;
  • lower the budget.

A request outside those limits is refused with an error that names the limit, so a run always uses exactly the settings it asked for. Guardrails and approvals stay exactly as published. Each run records the settings it used. Chat applies this today through a settings panel on each thread; the run API that gives other callers the same controls is planned.

Why tools only narrowThe tool list is what the publish review approved. Letting a caller add a tool would let anyone with run access widen what the agent can do to business systems without a review. Narrowing is always safe, so it needs no approval.

One run API for every caller

Chat sends one run per message on a thread. A job is a background run with a goal. An agent test and the workflow agent step are runs with a fixed input and an output schema.

Why one run APIA fix to budgets, approvals or audit lands once and applies to chat, jobs, tests and workflows alike. Separate paths into the kernel drift apart and each needs its own review.

6 Workflows

A workflow is a graph of typed nodes that runs the same steps every time. Each step is recorded in a journal: after a crash the run resumes from the journal, and every write is reconciled by its key, so a payment is sent once. Workflow definitions are data, so authors compose them in the editor and write no engine code.

Engine core

built

Flow control, human review steps, the step journal, the work queue, workers, leases with generation fencing, and reconcile-by-key for writes. LangGraph is the runner underneath.

Node types and the Node SDK

partial

A node type owns every fact about a step: ports, parameters, effects class, retry and executor. The editor, the validator and the runner all read the same registry entry. Seven types ship today (request trigger, set data, if, tool action, agent, human review, end) from a catalogue of 24 (22 steps and 2 attachments). Schedule, email, chat, webhook and poll start runs as triggers. The SDK for writing new ones is planned.

Why one registryWhen the form, the validator and the runner each keep their own copy of a step's rules, they drift and a workflow that saves cleanly fails at run time. One entry read by all three keeps them in agreement.

Node packs

planned

Node types ship in packs: ai, tools, files, agents and channels. Packs are installed at deploy time from an allowlist pinned by hash, and each journal row records the hash of the code that ran it.

Why packs install only at deploy timeA pack is code that runs inside the platform. Installing it only from a reviewed allowlist at deploy time means every step in the journal can be traced to the exact code that ran it, and the only code that reaches production is code that passed review.

Triggers

partial

Triggers are adapters on one start API, each with a dedupe key and window. Request triggers are built; email, chat, schedule, event and poll triggers follow.

Why one start APIEvery trigger then gets the same duplicate protection and the same audit record, and one trigger can start either a workflow or an agent job.

4 Chat and UI

People reach Ops AI through the console, and systems and customers reach it through channels. Every surface starts runs through the same public APIs that the SDK uses.

Console

partial

A Next.js app with sections for agents, workflows, chat, cases, reviews, knowledge, tools, access and audit. Every screen reads through one API contract, so the same build runs on an in-memory mock or on the services. The console calls each service directly at its own URL, signed in through platform-service. On services today: chat, agents, skills, guardrails and widgets, workflows, reviews, tools, secrets, the egress allow list, the tool call log, knowledge and storage settings, the Files page (which lists, searches, filters, downloads, deletes in bulk and places holds on files-service when its address is set, and hides setting retention and exporting evidence until the service offers them) and, with real sign-in, members, access and the audit log. On mock data: assurance and evals, model risk, prompt blocks, integrations, deployments and Cases; a page that still shows sample data carries a Preview mark while real services answer beside it.

Why one contractScreens can be designed, reviewed and demonstrated before their service exists, and switching an area to the real service is a setting. The contract also stops a screen from joining data itself: counts and joined views come from the API.

Chat

built

A thread of runs on one agent, one run per message. Answers stream with citations, tables and charts, and a drafted action appears as an approval card in the thread. A banker can attach a file to a message (PDF, text, Markdown, CSV or Word, up to 10 MB) and, within the agent's limits, choose the model, temperature, tools and knowledge for a thread. An agent can show a table, chart or form from a widget template that a builder published through a review. When a conversation uses up its budget, the chat shows a card instead of an error: the person who started it can continue, and an admin of its team can raise the cap.

Channels

partial

A channel is a trigger: it turns what arrives into a run on a published version. The REST API and the shared mailbox start runs today; the mailbox runs on a test mail source, and a real mail tenant is next. An agent's chat can be embedded on an intranet page: a team creates a widget deployment that pins one published version of the agent and lists the exact page origins allowed to use it, and the page loads one script tag. An MCP endpoint that offers agents to AI clients is planned.

The page never holds a long-lived key. It gets a session that lasts 15 minutes and works only for that deployment, that origin and that person. The session comes from the bank's single sign-on token, or from the bank's own server with a team API key. Messages are limited to 60 a minute per deployment and 10 per person; today the count is kept inside one process.

Why the page gets a sessionA key placed in a page can be copied by anyone who opens it. A session that expires in 15 minutes and works for one deployment, one origin and one person limits what a copy is worth.

One work list

planned

Agents and workflows publish the same work-item contract, so Cases, Reviews and Overview list agent jobs and workflow runs together, already joined by the API.

1 Access control

Every request passes the same checks in order. Access is granted per team, and a person can hold a different role in each team they belong to. platform-service is the only issuer of identity tokens; every other service verifies them locally against a published key set.

Authentication

A short-lived token from platform-service, or a team API key. Federation with an enterprise IdP (Entra ID, Okta, Keycloak) over OIDC is planned.

Tenant isolation

Each tenant sees only its own records; a request for another tenant's record returns 404, which keeps its existence private. Row-level security protects run, checkpoint, workflow and identity tables; the data gateway and knowledge filter by tenant in each query.

Team scoping

The token lists the caller's teams. A record in another team of the same tenant answers 403 and names the owning team.

Authorization (RBAC)

One role per team, from the table below. API keys are read or write; a read key is limited to reads.

Policy and approval

A write to a system of record also needs an approval token for that exact input, checked by OPA at the data gateway.

8 Data gateway built

tools-service is the only way an agent or a workflow reads from or writes to a business system. Each system is a tool module: imported from an OpenAPI description or an MCP server, reviewed by the security team, then published.

Connections

  • REST APIs, from an OpenAPI description.
  • MCP servers, through the gateway's MCP client over streamable HTTP: tools are discovered with tools/list and called with tools/call. MCP servers are reached over HTTP only.
  • Credentials are stored encrypted and stay in the gateway; agents and workflows receive results, with masked fields redacted.
  • Agents and workflow tool steps call the gateway over HTTP with a service token.
  • An MCP server that offers platform tools to outside clients is planned.

Controls on every call

  • An approval policy per operation, with step-up sign-in where the policy asks for it.
  • Rate and amount limits held in the database, so they apply across every gateway process.
  • The security team's approver or admin reviews each module before it is published.
  • A write carries an approval token bound to its input hash and the run's lease generation; OPA accepts it once, for that input, from the current run.
  • Calls reach only allow-listed hosts at checked addresses.
  • Every call is logged with its verified caller and reconciled by key.
  • Each secret lists the operations that read it, can be limited to chosen teams, and cannot be deleted while an operation uses it. A call from a team the secret does not allow is refused before anything is sent.

Tool workbench

built

A builder opens one operation on its own page, edits the call and its input, and runs it against the mock or the test environment. A draft mock response and a draft response transform are tried without being saved, so agents keep calling the published version until the change goes through review. A secret can be typed for a single run; it is not stored, logged or returned, and the request shown has it masked. The page lists the gateway's steps in order.

Why drafts run unsavedA builder can see what a change does before it is staged for review, and a test cannot alter what a live agent receives.
Why two egress gatewaysA tool call acts on a system of record and needs an approval per call; a model call spends budget and needs a key per identity. Giving each its own gateway keeps business-system credentials and model-provider keys in separate processes, so a risk review can examine each path alone, and agent workers hold neither.

7 Shared services

Services that agents and workflows both use. Each is a package with its own API, so a deployment with only agents, or only workflows, keeps every one of them.

Identity and teams

partial

platform-service: sign-in, sessions, tenants, teams, roles, invites, API keys and the audit log. A new person accepts an invitation through its link and is signed in. A person who already has an account accepts only while signed in as themselves, and the check runs inside the same database transaction as the acceptance, so an account created a moment earlier is still found. Team ownership on every entity is being completed.

Why an existing account signs in to acceptAn invitation link can be forwarded or read by anyone with access to the mailbox. If the link signed in the account it names, whoever held it would act as that person in every team they belong to.

Reviews and cases

built

One review contract any producer opens and resumes by key, and one queue for people. A decision mints an approval token for the exact input and resumes the waiting run once. Served by agents-service today; moving into its own package, ops_hitl.

Triggers and timers

partial

One registry that starts an agent job or a workflow run, plus SLA timers that fire each outcome once. Moving into its own package, ops_triggers.

Knowledge

built

kb-service: knowledge bases, their sources and passages cited by page and section. Deleting a base leaves a record, so an agent that cited it keeps its other bases.

Files

partial

files-service (port 8750) stores file bytes. An admin on the Security team chooses where each kind of file goes (a local folder, S3 or Azure Blob), under which credential and limits. Every new or changed target is tested with a small write, read and delete before the setting is saved, and credentials are sealed and never shown again. The service checks size, type and digest, keeps one stored copy per team for identical content, keeps versions, blocks deletion while a file is in use, and applies legal holds. A retried upload returns the first file. The file list answers search, an upload-date range, filters on purpose, scan result and sensitivity, and a count for each view (quarantined, under legal hold, unused for 30 days, expiring within 30 days) from the database query. A file that is used, held or still retained says why it cannot be deleted, and a bulk delete skips each such file and names the reason. The S3 target is tested against a mock S3 service and the Azure Blob adapter against an Azure emulator when one is running; no real cloud account has been used yet. Retention jobs, resumable large uploads, the console upload component and virus scanning (off for now) are planned. The knowledge service stores its uploads through it.

Work feed and audit

planned

One work-item contract that agents and workflows both publish, and one view of who did what across tool calls, model calls and decisions.

Runs

A run is one piece of work by an agent or a workflow, with a status, a budget and an event stream. Workflow runs use these states today; agent runs adopt them with the run API (planned).

StateMeaning
queuedAccepted and waiting for a worker
runningA process holds the run's lease and is executing it
waitingPaused for a person, a timer or another run; the reason says which
succeeded, failed, cancelledFinished, with a reason recorded for each failure or cancellation

A pause waits in place

A run that needs a person moves to waiting, releases its lease and keeps its checkpoint. The decision resumes the same run. Waiting runs are kept for up to seven days.

Why wait in placeOne run keeps one budget, one audit trail and one event stream across every approval, so a reviewer and an auditor see a single record. Releasing the lease while waiting keeps every worker free during a pause of hours or days.

Durable by default

Each step is checkpointed. A running run holds a lease; if its process stops, a sweeper in another process takes the expired lease, raises the generation and continues from the last checkpoint. In testing, recovery started about 5.5 seconds after a process was killed.

Versions are pinned

Definitions are immutable and identified by version and digest. A run keeps the version it started on through every later publish, and an operator can migrate a waiting run deliberately.

Service map

A service is a package with API routes, background loops and its own database migrations. Each is named after the console section it serves. Today each service runs as its own process; a single host program, ops-host, that starts any set of them in one process is the first part of version 1.

Each service owns its data

Every service has its own tables and migration chain and reads only its own. Services exchange data through their APIs, and each call between services is signed with the caller's own key.

WhyA service can then change its tables, move to its own database or be removed without breaking another service. It also gives a clear answer to "which component can read this data", which a risk review asks for every table.

Imports run one way

Shared packages come first, then the workflow engine, then each service's activities, graphs, stores and API. The commit gate checks that order on every commit and keeps the workflow engine independent of the agent runtime. Services are moving to a domain, use case, adapter and API layout.

10 Database dependency

The platform connects to a SQL database the enterprise runs, usually a managed instance owned by its data team. Each service may have its own database or share a server. Development uses a local PostgreSQL 17 container, and unit tests use SQLite. Every table, its owning service, keys and status are on the data model page.

Supporting PostgreSQL, Azure SQL and MySQL means Ops AI runs on the engine already approved. Putting tenant isolation in the store layer is what makes that possible, because row-level security exists on only some of them.

Develop

Everything runs from the root Makefile. Prerequisites: Python 3.12, uv, Node 20 or later with pnpm 10, and Docker for the development PostgreSQL and OPA. A model key (OPENAI_API_KEY, or ANTHROPIC_API_KEY for a claude-* alias) is needed only for real chat; every service starts without one and reports it on /health.

Why a MakefileOne entry point for install, verify, run and deploy, the same on a laptop and in CI. A new engineer runs the same three commands as the build server, and each service answers the same set of verbs.

Console only

Runs on in-memory data alone. Suited to screen work and demos.

  • pnpm install then make dev, at localhost:3016.
  • State lives in memory and resets on reload.
  • ?mock=slow, ?mock=error and ?mock=empty show each loading, error and empty state.

Full stack

Deploy

The same packages run in three layouts; only the host's flags change. Every release runs on one virtual machine with plain systemd, and Compose and Kubernetes are optional.

One process

partial

Every service in one process. For evaluation, development and tests. Today make up runs each service as its own local process; the single-process host, ops-host, is the first part of version 1.

One virtual machine

planned

systemd units for a web process (all routes), a loops process (workers, sweepers, schedules, SLA timers) and separate tools and models processes, with PostgreSQL managed or on the VM, the OPA binary, and local disk or an object store.

Split services

planned

A Kustomize base per service and an overlay per environment, each service scaled on its own. Compose today covers the development PostgreSQL and OPA.

Why three layoutsOne process is the fastest way to evaluate and develop. A single VM fits a small production deployment and bank estates that run plain virtual machines. Split services fit when load or a security boundary needs a component on its own. Because the code is identical in all three, a use case that passes in one passes in the others.

Operations

Configuration comes from the process environment through one settings class per process. Every variable uses the OPS_ prefix, plus the provider key names.

Secrets

dependency

The enterprise secrets manager (Vault, Azure Key Vault, AWS Secrets Manager) places values in the process environment. Tool credentials are read only by the data gateway, provider keys only by the AI gateway and storage credentials only by the files service. In test and production a service starts once its review key and secrets key are set.

Why environment onlyEvery secrets manager can populate the environment, so the platform needs no integration per vendor, and rotation is a change in the secrets manager followed by a restart.

Runbooks

Stuck run

  • The run's state shows its status, next step, pending approval and SLA timers.
  • Its journal shows each attempt's owner and generation.
  • Running after its owner stops: the sweeper continues it after TTL plus one sweep. Waiting: it is with a person. Failed: fix the cause and resume from the last good checkpoint, or route it to people with a reason.

Bad version published

  • Publish the previous definition again so new runs take it.
  • Waiting runs can be migrated to a version where their waiting step exists.
  • Running runs on the bad version can be routed to people in one call.

Key rotation

  • Review key: set the new value on agents and tools, restart both, re-approve open reviews.
  • Service keys: add the new public key beside the old one on every callee, restart, then retire the old key.
  • Model keys and the database credential: change them in the secrets manager and restart.
